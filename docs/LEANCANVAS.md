## 1. 문제 (Problem)

**채용 담당자·면접관**

- 이력서 PDF 한 장만으로는 주니어 지원자의 실제 기여도와 문제 해결력을 검증하기 어렵다.
- 지원자별 포트폴리오 형식이 제각각이라 3분 안에 경력·프로젝트·자격을 훑기 힘들다.
- 연락 수단이 흩어져 있어 관심이 생겨도 바로 문의하기 번거롭다.

**지원자 본인(함상현)**

- 비전공에서 IT로 전환한 이야기와 인프라·클라우드·웹 개발을 아우르는 경력이 이력서 형식에 다 담기지 않는다.
- 이력서·프로젝트·글이 여러 곳에 흩어져 있어 갱신할 때마다 배포나 파일 교체가 필요하다.
- 공고마다 노출하고 싶은 정보(예: 어학 점수)가 달라 매번 이력서를 따로 손봐야 한다.

**기존 대안**: PDF 이력서, 노션 포트폴리오, 외부 블로그 플랫폼, GitHub 프로필

## 2. 고객 세그먼트 (Customer Segments)

| 구분                     | 대상                                     | 설명                                                                      |
| ------------------------ | ---------------------------------------- | ------------------------------------------------------------------------- |
| **핵심 고객**            | 채용 담당자·면접관 (방문자)              | 주니어 백엔드 개발자 채용을 검토하며 짧은 시간에 지원자를 판단하려는 사람 |
| **사용자 (콘텐츠 운영)** | 함상현 본인 (관리자 1인)                 | 모든 콘텐츠를 웹에서 직접 관리하는 사이트 주인                            |
| **얼리 어답터**          | 지원서에 링크를 받아 보는 첫 채용 담당자 | 1차 공개 직후 지원한 회사의 담당자                                        |

- 방문자 계정·회원가입은 없다. 방문자는 로그인 없이 모든 공개 페이지를 본다.

## 3. 가치 제안 (Unique Value Proposition)

> **"3분 안에 주니어 백엔드 개발자 함상현의 경력·프로젝트·자격을 확인하고, 바로 이력서를 받거나 연락할 수 있는 포트폴리오."**

- **한 곳에서 검증**: 경력·학력 타임라인, 프로젝트 케이스 스터디(문제 → 역할 → 기술 → 성과), 자격·어학·논문을 한 사이트에 정리한다.
- **실제 데이터만 노출**: 수치는 실제 데이터(경력 기간, 자격증 수, 석사 학점 등)에서 계산하고 임의 수치는 쓰지 않는다.
- **바로 행동**: 이력서 PDF 다운로드와 연락 폼(이메일 알림)을 홈·연락 페이지에서 바로 제공한다.
- **전문성 증명**: 직접 운영하는 MDX 기술 블로그로 글쓰기와 학습 이력을 뒷받침한다.

**상위 개념 (High-Level Concept)**: 채용 담당자를 위한 "개발자 이력서 + 케이스 스터디 + 기술 블로그" 원페이지 포트폴리오

## 5. 경쟁우위 (Unfair Advantage)

- **전환 스토리 + 인프라~웹 경력**: 비전공에서 IT로 전환했고 웹정보시스템 개발·유지보수, 클라우드 전환, 온프레미스 인프라까지 경험한 이력은 쉽게 복제되지 않는다.
- **검증 가능한 실제 이력**: 자격증, 석사 학위·논문, 프로젝트 성과 등 증빙 가능한 데이터만 노출한다.
- **직접 운영하는 사이트 자체가 포트폴리오**: Next.js 16(Cache Components), Supabase, Drizzle, Better Auth, MDX 렌더링 등 사이트 구현이 곧 기술 역량의 증거다.
- **배포 없이 갱신하는 운영 구조**: 3차 이후 글·프로젝트·이력서를 웹에서 바로 수정한다.
- **개인 도메인·브랜드**: `hkoikoi.dev` (도메인 구매 여부 확인 필요)

## 6. 수익 흐름 (Revenue Stream)

직접적인 금전 수익은 없다. 이 사이트의 성과는 **취업 기회**로 환산한다.

| 구분      | 내용                                                      |
| --------- | --------------------------------------------------------- |
| 직접 수익 | 없음 (광고·구독·판매 모델 없음)                           |
| 간접 수익 | 서류 통과율 상승, 면접 제안 증가, 채용 담당자의 직접 연락 |
| 장기 가치 | 기술 블로그를 통한 개발자 브랜딩과 인바운드 제안          |

## 8. 주요 지표 (Key Metrics)

> PRD는 목표 수치를 정하지 않았다. 아래 지표는 **[제안]**이며 목표치는 1차 공개 후 정한다.

| 단계                | 지표                                    | 측정 방법                                                                                          |
| ------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 유입 (Acquisition)  | 지원서 링크 경유 방문 수                | 방문 분석 도구 [제안]                                                                              |
| 활성화 (Activation) | 프로젝트 상세 조회 비율, 평균 체류 시간 | 방문 분석 도구 [제안]                                                                              |
| 전환 (Conversion)   | 이력서 다운로드 수, 연락 폼 제출 수     | 다운로드 이벤트, `ContactMessage` 저장 건수                                                        |
| 성과 (Outcome)      | 면접 제안 수, 서류 통과율               | 본인 기록 [제안]                                                                                   |
| 콘텐츠 (Content)    | 발행한 글 수, 블로그 방문 수 (2차~)     | `Post` 발행 건수, 방문 분석 도구                                                                   |
| 품질 (Quality)      | 완료 기준 달성 여부                     | 1차: 지원서에 링크를 넣을 수 있음 / 2차: 관리자에서 글 발행 가능 / 3차: 배포 없이 주요 콘텐츠 수정 |

## 9. 채널 (Channels)

| 구분          | 채널                                       | 비고                   |
| ------------- | ------------------------------------------ | ---------------------- |
| **핵심 채널** | 입사 지원서·이력서에 포함하는 사이트 링크  | 1차 공개의 목적        |
| **연결 채널** | GitHub 프로필·저장소, 이메일 서명 [제안]   | GitHub·이메일만 공개   |
| **콘텐츠**    | 기술 블로그 글 (검색 유입, 2차~)           | 전문성 증명 + 인바운드 |
| **전환 채널** | 연락 폼 + 이메일 알림, 이력서 PDF 다운로드 | 사이트 내 행동 유도    |

## 가정·검증 필요 사항

- **고객 가정**: 채용 담당자는 포트폴리오를 3분 안팎으로 훑는다. 실제 체류 시간으로 검증한다.
- **가치 가정**: 케이스 스터디 형식의 프로젝트 설명이 PDF 이력서보다 서류 통과에 도움이 된다.
- **콘텐츠 공백**: 프로젝트별 역할·기술·성과, 고객사 공개 가능 범위, 학위 논문 제목·초록·키워드, 주력 기술 스택, 프로필 사진이 필요하다.
- **개인정보**: 연봉, 자격증 등록번호, 퇴직사유, 고등학교 정보는 노출하지 않는다.
- **MVP 이후**: 사회활동 노출, 문의 내역 열람 화면, 댓글·검색·RSS, 영문 지원, 라이트 모드는 제외했다.
